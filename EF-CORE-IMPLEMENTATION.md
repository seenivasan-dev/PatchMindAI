# EF Core Persistence Layer Implementation

## Overview
Successfully replaced in-memory repositories with EF Core + SQLite backend. All public interfaces remain unchanged - the implementation is swappable without affecting API or Web layer code.

## Changes Made

### 1. Dependencies Added
- **Microsoft.EntityFrameworkCore.Sqlite** (9.0.8) - SQLite provider
- **Microsoft.EntityFrameworkCore.Design** (9.0.8) - CLI migration support
- **dotnet-ef CLI** (10.0.8) - Global tool for managing migrations

### 3. Modified Files

#### DI Configuration
**[DependencyInjection/InfrastructureServiceCollectionExtensions.cs](src/PatchMindAI.Infrastructure/DependencyInjection/InfrastructureServiceCollectionExtensions.cs)**
- Added `services.AddDbContext<PatchMindDbContext>()` with SQLite
- Reads connection string from `configuration.GetConnectionString("PatchMindAIDb")`
- Replaced singleton repositories with **scoped** EF implementations:
  ```csharp
  services.AddScoped<IAnalysisJobRepository, EfAnalysisJobRepository>();
  services.AddScoped<IAnalysisResultRepository, EfAnalysisResultRepository>();
  ```
- Reason for scoped lifetime: DbContext manages database sessions per logical operation; singleton lifetime would create connection pooling issues

#### API Program.cs
**[src/PatchMindAI.API/Program.cs](src/PatchMindAI.API/Program.cs)**
- Added migration auto-apply on startup:
  ```csharp
  using (var scope = app.Services.CreateScope())
  {
      var context = scope.ServiceProvider.GetRequiredService<PatchMindDbContext>();
      context.Database.Migrate();
  }
  ```
- Ensures schema is created and all migrations applied before app begins

#### Background Worker
**[src/PatchMindAI.API/Background/AnalysisJobWorker.cs](src/PatchMindAI.API/Background/AnalysisJobWorker.cs)**
- Refactored to use `IServiceScopeFactory` pattern
- Singleton service can't directly inject scoped repositories
- Solution: Create a new scope per job processing iteration:
  ```csharp
  using (var scope = _serviceScopeFactory.CreateScope())
  {
      var jobRepository = scope.ServiceProvider.GetRequiredService<IAnalysisJobRepository>();
      var resultRepository = scope.ServiceProvider.GetRequiredService<IAnalysisResultRepository>();
      // ... use scoped instances
  }
  ```

#### Configuration
**[src/PatchMindAI.API/appsettings.json](src/PatchMindAI.API/appsettings.json)**
- Added Persistence provider config:
  ```json
  "Persistence": {
    "Provider": "EfCore"
  }
  ```
- ConnectionString already configured: `"Data Source=patchmindai.db"`

## How It Works

### Data Flow
1. **Job Creation** → HomeController (Web) → POST /api/analysis/jobs (API)
2. **API Validates** → Creates AnalysisJob via `IAnalysisJobRepository.CreateAsync()`
3. **EF Saves** → INSERT into AnalysisJobs table in patchmindai.db
4. **Cache Write-Through** → Also saves to InMemory cache for fast reads
5. **Job Queued** → Message sent to IAnalysisJobQueue (in-memory channel)
6. **Worker Processes** → Dequeues, creates scope, fetches job from DB
7. **Orchestrator Runs** → Generates analysis result
8. **Results Persisted** → INSERT into AnalysisResults table
9. **Status Update** → Job marked Completed, AnalysisJobs row updated
10. **Result Retrieval** → HomeController queries cache or falls back to EF

### Key Design Decisions

#### Why Scoped Repositories?
- **DbContext**: Owns database connection/transaction scope
- **Per-Request**: ASP.NET HTTP requests get their own DbContext instance (scoped by default)
- **Thread-Safe**: EF DbContext is NOT thread-safe; scoping ensures isolation

#### Why Migrate on Startup?
- Developers don't need to remember `dotnet-ef database update`
- Schema automatically matches deployed version
- Safe for multi-instance deployments (EF uses locking mechanism)

#### SQLite vs Other Databases
- **Development**: SQLite requires no server installation; file-based storage
- **Production Path**: Connection string can be swapped to PostgreSQL/SQL Server without code changes
- **Migration Path**: All EF migrations remain compatible
